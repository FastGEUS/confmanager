# ConfManager

Система учёта конференции: участники, заявки на доклады и оргвзносы.
Учебный проект по курсу «Metodologiya i praktiki DevOps» (ЛР1 — сквозной проект и Git-процесс, тема 4 «Конференция»).

## Стек

- FastAPI (HTTP API + веб-интерфейс на Jinja2)
- SQLAlchemy (ORM)
- SQLite по умолчанию для локальной разработки (переключается на PostgreSQL через `DATABASE_URL`)
- JWT-авторизация (роль "оргкомитет")

## Быстрый запуск

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload
```

Приложение поднимется на `http://localhost:8000`.
- Веб-интерфейс: `http://localhost:8000/`
- Документация API (Swagger): `http://localhost:8000/docs`
- Проверка работоспособности: `http://localhost:8000/health`
- Текущая версия: `http://localhost:8000/version`

## Сущности (MVP, ЛР1)

- **Participant** — участник конференции (ФИО, email, организация).
- **Application** — заявка на доклад (тема, статус: new/under_review/accepted/rejected).
- **Fee** — оргвзнос, связанный с заявкой (сумма, статус оплаты).

Полное описание — в `docs/schema.md`.

## Обязательное бизнес-правило

Оргвзнос (`Fee`) можно отметить оплаченным (`POST /fees/{fee_id}/pay`) **только если** связанная заявка (`Application`) имеет статус `accepted`. При попытке оплаты для заявки в статусе `new`, `under_review` или `rejected` API возвращает `400 Bad Request` с описанием причины.
Реализация: `app/crud.py`, функция `mark_fee_paid`.

## Правила внесения изменений

- Любое изменение проходит через отдельную задачу (issue) → отдельную ветку → несколько коммитов → Pull Request → слияние в `main`.
- Прямые коммиты в `main`, минуя ветку и PR, не допускаются.
- Запрещено удалять тесты, отключать линтеры/анализаторы или снижать пороги качества только для прохождения проверки (актуально начиная с ЛР3, когда появятся автотесты).
- Критические файлы (Makefile, настройки CI, тесты) — изменяются только через видимый в PR diff, с отдельным вниманием при код-ревью.
- Секреты и локальные файлы (.env, БД, кэш) не должны попадать в репозиторий — см. `.gitignore`.

## Порядок приёмки (эта ЛР1)

1. Показать путь изменения: issue → ветка → коммиты → PR → merge.
2. Объяснить правила внесения изменений (см. выше).
3. Внести небольшое изменение через ветку и PR прямо на защите.
4. Показать, что секреты и `.env` не попадают в репозиторий.
5. Продемонстрировать тег `v0.1.0`.
