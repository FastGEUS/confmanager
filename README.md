# ConfManager

Учебный проект по дисциплине «Методология и практики DevOps», тема 4 «Конференция». ЛР1: учёт участников, заявок на доклады и оргвзносов. Проект выполняется индивидуально.

Стек: Python 3.11+, FastAPI, SQLAlchemy, SQLite, Jinja2 и JavaScript. PostgreSQL используется при развёртывании в ЛР2.

## Запуск

Из корня проекта:

```bash
python -m venv .venv
```

Linux/macOS: `source .venv/bin/activate`. Windows PowerShell: `.venv\Scripts\Activate.ps1`.

```bash
python -m pip install -r requirements.txt
python -m app.manage setup
python -m app.manage create-committee --email committee@example.org
python -m app.manage run
```

`setup` создаёт `.env` со случайным ключом JWT и таблицы БД. Существующая конфигурация и данные сохраняются. Пароль оргкомитета вводится скрыто, 12–128 символов. Команда не повышает права уже зарегистрированного участника.

- Интерфейс: <http://127.0.0.1:8000/>
- Документация API: <http://127.0.0.1:8000/docs>
- Служебные адреса: `/health`, `/ready`, `/version`

Настройки описаны в `.env.example`. Переменные окружения имеют приоритет над `.env`. Основные настройки: `DATABASE_URL`, `SECRET_KEY`, `APP_HOST`, `APP_PORT`, `ACCESS_TOKEN_EXPIRE_MINUTES`. Пример SECRET_KEY нужно заменить случайным ключом длиной не менее 32 байт; команда setup делает это автоматически. Для разработки можно запускать `python -m app.manage run --reload`.

## Функции и правила

Участник регистрируется, входит, подаёт тему и видит свои заявки. Оргкомитет видит все заявки, меняет их статусы, назначает оргвзнос и отмечает оплату. Права проверяются по БД; регистрация создаёт обычного участника.

Оплату можно отметить только для заявки accepted. Оплаченная заявка остаётся принятой, повторная отметка не меняет время оплаты. У одной заявки один взнос. Сумма положительная и содержит не более двух десятичных знаков. Это учёт оплаты, перевод денег приложением не выполняется.

## Проверка перед сдачей и PR

```bash
python -m pip check
python -m compileall -q app
```

Затем проверить в интерфейсе и Swagger:

1. Зарегистрировать участника, войти и подать заявку. Без входа подача должна вернуть 401; второй участник не видит чужую заявку.
2. Войти оргкомитетом и назначить взнос. Оплата заявки new должна вернуть 400. Перевести заявку в accepted и отметить оплату — статус paid.
3. Повторная оплата сохраняет paid_at; перевод оплаченной заявки в rejected возвращает 400.
4. Проверить неверный email, пустую тему и отрицательную сумму — 422; неверный пароль — 401.
5. Перезапустить приложение: данные сохраняются. Проверить `/health`, `/ready` и `/version`.

`git check-ignore .env confmanager.db` должен показать оба файла; `git ls-files .env confmanager.db` ничего не выводит.

## Правила изменений

Изменения проходят через GitHub issue → отдельную ветку → осмысленные коммиты → PR → просмотр diff → слияние. Перед PR обязательны команды и сценарии выше. При работе в одиночку проверка изменений самостоятельная и отмечается в PR.

Запрещено добавлять секреты и локальную БД, переписывать общую историю, вносить изменения в main в обход PR или убирать проверки ради прохождения ошибки. Первая версия обозначается тегом v0.1.0. На защите нужно показать Git-процесс, разрешённый конфликт и небольшое изменение через новый PR.

Далее: ЛР2 — Linux и PostgreSQL; ЛР3 — автотесты, миграции и резервное копирование; последующие работы — контейнеры и CI/CD. Приглашения, тезисы и гостиничные заявки добавляются при дальнейшем развитии темы.
