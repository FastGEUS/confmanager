# ConfManager

Учебное приложение для учёта конференции по дисциплине «Автоматизация процессов жизненного цикла программных средств / Методология и практики DevOps». Тема 4 «Конференция». Проект выполняет один разработчик; ЛР1 реализует участников, заявки на доклады и оргвзносы.

## Установка и запуск

Нужен Python 3.11 или новее. Проверено на Python 3.12.14 и 3.14.7. Выполните команды из корня репозитория:

```bash
python -m venv .venv
```

Активируйте окружение: Linux/macOS — `source .venv/bin/activate`; Windows PowerShell — `.venv\Scripts\Activate.ps1`.

```bash
python -m pip install -r requirements.txt
python -m app.manage setup
python -m app.manage create-committee --email committee@example.org --name "Оргкомитет"
python -m app.manage run
```

`setup` создаёт локальную `.env` со случайным ключом JWT и таблицы SQLite. Существующая `.env` сохраняется; БД не очищается. Пароль оргкомитета вводится скрыто с подтверждением (12–128 символов). Команда не повышает права существующего участника. Если email уже занят, используйте другой email.

- Интерфейс: <http://127.0.0.1:8000/> — регистрация, вход, подача заявки; для оргкомитета — статусы и взносы.
- Swagger UI: <http://127.0.0.1:8000/docs> — кнопка Authorize, username равен email.
- `/health` — жив ли HTTP-процесс; `/ready` — отвечает ли БД; `/version` — версия приложения.

Для разработки: `python -m app.manage run --reload`. Не используйте reload при развёртывании.

## Настройки

Реальные переменные окружения имеют приоритет над `.env` в корне проекта. `.env.example` описывает настройки, но содержит непригодный для запуска пример ключа. Не копируйте его без замены ключа.

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | По умолчанию `sqlite:///./confmanager.db`; для ЛР2 — `postgresql+psycopg2://user:password@host/database` |
| `SECRET_KEY` | Обязательный случайный ключ, минимум 32 байта; публичные заглушки отклоняются |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Время жизни JWT, 1–1440 минут, по умолчанию 60 |
| `APP_HOST`, `APP_PORT` | Адрес и порт команды run, по умолчанию 127.0.0.1:8000 |
| `CONFMANAGER_ENV_FILE` | Другой путь к env-файлу; пустая строка отключает загрузку файла |

Стек: FastAPI, Jinja2 и JavaScript, SQLAlchemy, SQLite или PostgreSQL, PyJWT, pwdlib. Новые пароли хешируются Argon2; старые bcrypt-хеши проверяются и обновляются при успешном входе. Схема исходной БД сохранена. Версионированные миграции запланированы в ЛР3.

## Правила предметной области и доступа

Участник видит свои заявки и подаёт заявку от своего имени. Оргкомитет видит все заявки, может подавать их за участника, менять статус и назначать взнос. Регистрация всегда создаёт обычного участника. Права читаются из БД при каждом защищённом запросе.

Взнос можно отметить оплаченным только для заявки `accepted`. Оплаченную заявку нельзя перевести в другой статус. Повторная отметка оплаты сохраняет исходное время оплаты. Для одной заявки допускается один взнос с положительной конечной суммой не более 9 999 999 999,99 рубля и двумя знаками после запятой. Изменение статуса взноса фиксирует учёт оплаты, интеграция с платёжным провайдером не реализована.

## Обязательные проверки

Команда проверки для Linux и Windows: `python -m app.manage verify`.

```bash
python -m pip install -r requirements-dev.txt
python -m app.manage verify
```

Команда последовательно выполняет `pip check`, Ruff lint, проверку форматирования, Bandit и 54 теста. Любая ошибка останавливает проверку. Для Make доступны `make setup`, `make run`, `make test`, `make quality`, `make verify`. Windows может использовать команды Python без Make. Описание проверок и обоснование двух локальных исключений анализатора — [verification.md](docs/verification.md).

## Правила изменений и приёмки

1. Опишите проблему и критерии приёмки в GitHub issue. Создайте отдельную ветку от актуального `main`.
2. Сделайте несколько осмысленных коммитов, выполните обязательную проверку и откройте PR со ссылкой на issue и результатами проверки.
3. Просмотрите diff, особенно тесты, Makefile и настройки проверок. При работе в одиночку зафиксируйте самостоятельную проверку в PR; не изображайте второго рецензента.
4. После успешной проверки слейте PR в `main`. Тег `v0.1.0` должен указывать на принятую первую версию.

Запрещены прямые изменения `main` в обход PR, добавление секретов и локальной БД, удаление проверок или снижение требований ради прохождения проверки, принудительное переписывание общей истории. Каждое обоснованное локальное исключение анализатора должно быть видно и объяснено в diff.

На защите покажите issue → ветку → коммиты → PR → merge → тег; разрешённый конфликт слияния; проверку отсутствия `.env` в Git; небольшое изменение через новый PR. Статус текущей подготовки и доказательства конфликта — [git-workflow.md](docs/git-workflow.md). Локальная [задача LR1-001](docs/tasks/LR1-001.md) до публикации не является GitHub issue.
