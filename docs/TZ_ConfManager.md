# Техническое задание на систему учёта конференции ConfManager

Редакция 1.0. Представляется преподавателю для согласования темы и требований. ТЗ определяет первую работоспособную версию для ЛР1 и направления дальнейшего развития сквозного проекта. Подпись об утверждении и результат приёмки оформляются преподавателем отдельно.

## 1 Общие сведения

Полное наименование — «Система учёта участников и заявок конференции». Условное обозначение — ConfManager. Основание разработки — задание по дисциплине «Автоматизация процессов жизненного цикла программных средств / Методология и практики DevOps», тема 4 «Конференция».

Учебный заказчик — преподаватель дисциплины; разработчик — владелец репозитория FastGEUS, работающий индивидуально. ФИО, группа и ФИО преподавателя указываются в отчёте и листе согласования при сдаче. Договор и внешнее финансирование отсутствуют. Плановые сроки этапов определяются календарём дисциплины; дата защиты согласуется с преподавателем.

Результат передаётся как исходный код, документы, история Git и тег версии в https://github.com/FastGEUS/confmanager. Изменения ТЗ оформляются отдельной задачей и PR с описанием влияния на приёмку. Разработка структуры документа опирается на ГОСТ 34.602-89, указанный в учебном задании.

## 2 Назначение и цели создания системы

Система предназначена для регистрации участников конференции, подачи и рассмотрения заявок на доклады, назначения и учёта оплаты оргвзносов. Цель первой версии — заменить разрозненные списки единым хранилищем, связать участника с заявкой и взносом и предотвратить отметку оплаты непринятой заявки.

Успех ЛР1 определяется воспроизводимой установкой, выполнением требований FR01–FR07, наличием HTTP API и веб-интерфейса, успешными проверками и подтверждённым процессом issue → ветка → коммиты → PR → merge → тег. Приглашения, тезисы и потребность в гостинице относятся к дальнейшему развитию темы.

## 3 Характеристика объекта автоматизации

Оргкомитет принимает заявки на доклады, рассматривает их, принимает или отклоняет, назначает оргвзнос и отмечает полученную оплату. Участник сообщает ФИО, email и организацию, подаёт тему и отслеживает состояние своей заявки. Оплата в ЛР1 фиксируется оргкомитетом вручную; приложение не переводит денежные средства.

Категории пользователей: гость, участник и оргкомитет. Гость регистрируется и входит. Участник работает со своими данными. Оргкомитет обрабатывает все заявки. Первую учётную запись оргкомитета создаёт оператор через локальную команду CLI, имея доступ к серверу и БД.

## 4 Требования к системе

### 4 1 Структура и функционирование

Приложение включает HTTP API на FastAPI, браузерный интерфейс на Jinja2 и JavaScript и реляционную БД через SQLAlchemy. Локальная демонстрация использует SQLite; PostgreSQL и системный сервис проверяются при развёртывании ЛР2. Данные должны сохраняться после штатного перезапуска процесса при неизменной DATABASE_URL.

Не менее трёх связанных сущностей обязательны в первой версии: Participant, Application, Fee. У участника может быть несколько заявок; у заявки не более одного взноса. Сервис не должен запускаться с отсутствующим или общеизвестным примером ключа JWT.

### 4 2 Функциональные требования первой версии

FR01 Регистрация участника. Гость передаёт ФИО, email, пароль и необязательную организацию. Успешный запрос создаёт обычного участника и возвращает 201. Повторный email отклоняется. Пароль хранится только как хеш и не возвращается в API.

FR02 Вход и текущий профиль. Пользователь входит по email и паролю, получает JWT с ограниченным сроком и может запросить свой профиль. Неверный пароль, отсутствующий или просроченный токен дают 401. Права определяются текущей записью БД при каждом запросе. Публичная регистрация и произвольная роль в JWT не дают административных прав.

FR03 Подача и просмотр заявок. Вошедший участник создаёт заявку с темой от своего имени; начальный статус new. Его список содержит только собственные заявки. Подать заявку за другого участника и просмотреть все заявки может только оргкомитет. Чужой participant_id от обычного участника отклоняется с 403.

FR04 Рассмотрение заявки. Оргкомитет меняет статус между new, under_review, accepted, rejected. Неизвестное значение отклоняется с 422. Только принятая заявка допускает отметку оплаты; после оплаты изменить accepted на иной статус нельзя.

FR05 Оргвзносы. Оргкомитет создаёт один взнос на существующую заявку. Сумма положительная, конечная, не больше 9 999 999 999,99 рубля и содержит до двух десятичных знаков. Повторное назначение взноса отклоняется. Оплата accepted переводит unpaid в paid и сохраняет время UTC; повторный запрос не меняет время. Оплата иной заявки возвращает 400.

FR06 Веб-интерфейс. В браузере доступны регистрация, вход, выход, подача темы и просмотр своих заявок. Оргкомитет получает список всех заявок, изменение статуса, назначение и отметку оплаты взноса. Интерфейс показывает ошибки запросов; данные пользователя выводятся как текст без исполнения HTML.

FR07 Эксплуатационные команды и служебные адреса. Оператор создаёт локальную конфигурацию и учётную запись оргкомитета через CLI. GET /health проверяет HTTP-процесс, GET /ready выполняет проверку БД, GET /version возвращает 0.1.0. При недоступной БД /ready возвращает 503 без строки подключения и секретов.

### 4 3 Надёжность и безопасность

SR01 Входные модели запрещают неизвестные поля, пустые ФИО и темы, некорректный email и недопустимые суммы. ФИО и организация ограничены 200 символами, тема — 500, пароль — 12–128 символами и не состоит только из пробелов. Ошибки модели дают 422.

SR02 Права проверяются на сервере. Пароли хешируются Argon2; ранее сохранённые bcrypt-хеши поддерживаются и обновляются при успешном входе. Минимальная длина случайного SECRET_KEY — 32 байта; срок токена по умолчанию 60 минут, допустимый диапазон 1–1440. Выход удаляет токен из текущей вкладки; выданный токен действует до истечения срока, удаления пользователя или смены ключа.

SR03 Конфигурация читается из переменных окружения с приоритетом над локальной .env. Секреты, БД и кэш исключаются из Git. Начальная конфигурация создаётся один раз и не перезаписывает существующую. Ошибки БД возвращают общее сообщение без внутренней строки подключения. Для внешнего размещения требуется HTTPS; локальная демонстрация работает на loopback HTTP.

SR04 Проверки зависимостей, линтер, форматирование, анализатор безопасности и тесты обязательны перед PR. Обоснованные локальные исключения анализатора документируются; отключать проверки ради успешного результата запрещено. Масштабирование, аудит всех действий, ограничение частоты запросов и SLA не входят в критерии первой версии.

### 4 4 Обеспечение и ограничения

Информационное обеспечение — таблицы participants, applications, fees, уникальные email и application_id взноса, внешние ключи и перечисления статусов. Сумма в исходной схеме хранится как Float; для следующих этапов предусмотрена миграция на Numeric/Decimal. В ЛР1 автоматическое изменение существующей схемы не допускается. Удаление данных через API не предусмотрено.

Программное обеспечение — Python 3.11 или новее, зависимости из requirements.txt; для разработки — requirements-dev.txt. Проверяемые среды: Python 3.12.14 и 3.14.7. Клиент — современный браузер с JavaScript. Веб-интерфейс и документы — на русском языке; технические статусы API — на английском.

Техническое обеспечение — компьютер с Python и браузером, локальная файловая система для SQLite; для PostgreSQL требуется отдельная БД и доступные реквизиты. Нагрузочные нормативы и обязательные аппаратные характеристики для учебной версии не устанавливаются.

Организационное обеспечение — разработчик ведёт задачи, ветки и PR; при индивидуальной работе явно фиксирует самостоятельное ревью. Оператор отвечает за размещение конфигурации и предоставление доступа оргкомитету. На защите используются учебные данные.

## 5 Состав и содержание работ

Этап ЛР1: согласование темы и ТЗ; разработка API, БД и интерфейса; валидация и авторизация; документация запуска; проверки; демонстрация Git-процесса и конфликта; первая версия v0.1.0.

Этап ЛР2: развёртывание на Linux с PostgreSQL и системным сервисом. Этап ЛР3: миграции, расширенные тесты, резервное копирование и восстановление. Последующие этапы: контейнеризация, CI/CD и эксплуатационные практики по заданиям дисциплины. Приглашения, тезисы, гостиничные заявки, очередь рассылки и отчёты оформляются дополнительными требованиями перед реализацией.

Сроки последующих этапов и расширений утверждаются в календаре дисциплины. Их перечисление не означает, что они уже реализованы в ЛР1.

## 6 Порядок контроля и приёмки

Предварительные испытания выполняет разработчик на чистом виртуальном окружении. Установка runtime-зависимостей, setup, создание оргкомитета и запуск должны завершаться успешно. Для проверки изменений устанавливаются dev-зависимости и запускается python -m app.manage verify; ошибка любой проверки блокирует приёмку PR.

Приёмочные испытания преподаватель проводит по docs/acceptance.md: регистрация и вход; подача заявки; изоляция двух участников; обработка оргкомитетом; запрет оплаты непринятой заявки; успешная и повторная оплата; запрет отклонения оплаченной; ошибки ввода; сохранение данных при перезапуске; служебные адреса.

Доказательства процесса включают реальную GitHub issue, отдельную ветку, несколько осмысленных коммитов, PR с результатами проверки, слияние в main и тег v0.1.0. Демонстрационный merge должен иметь реальный конфликт и его разрешение. Локальная запись задачи не заменяет GitHub issue. Тема и ТЗ считаются согласованными только после подтверждения преподавателя; настоящая редакция не является протоколом приёмки.

## 7 Подготовка объекта к вводу в действие

Оператор устанавливает Python, создаёт виртуальное окружение и зависимости, выполняет setup, хранит .env вне Git, создаёт оргкомитет и запускает процесс. Перед изменением существующей БД делает резервную копию файла SQLite. Для ЛР2 подготавливает отдельную PostgreSQL БД и переменные окружения сервиса. Инструкции размещены в README.

Внешнее размещение требует HTTPS и ограничения доступа к административным реквизитам. Формализованные процедуры миграции, резервного копирования и восстановления разрабатываются в последующих лабораторных и проверяются до их использования с ценными данными.

## 8 Требования к документированию

В репозитории поставляются README с установкой, настройками и обязательными проверками; .env.example без реальных секретов; docs/api.md; docs/schema.md; настоящее ТЗ в Markdown и DOCX; docs/acceptance.md; docs/verification.md; docs/git-workflow.md и запись задачи. Документы изменяются вместе с кодом через PR.

Отчёт для защиты оформляется по титульному образцу дисциплины с фактическими ФИО, группой, преподавателем и годом. Титульный лист отчёта и лист утверждения ТЗ заполняются при сдаче; неизвестные персональные сведения не заменяются вымышленными. Документы передаются через репозиторий, отчёт — в согласованном с преподавателем формате.
